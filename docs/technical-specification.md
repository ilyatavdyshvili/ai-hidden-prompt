# Техническое задание
## ИИ-сервис обнаружения скрытых промптов в изображениях

**Тип работы:** дипломный проект / выпускная квалификационная работа  
**Версия:** 1.0  
**Назначение:** проектирование и последующая разработка прототипа интеллектуального сервиса

---

## 1. Общие сведения

### 1.1. Наименование

«ИИ-сервис обнаружения скрытых промптов в изображениях».

### 1.2. Назначение системы

Система предназначена для автоматизированного обнаружения текстовых инструкций, намеренно размещённых в изображениях таким образом, чтобы они были малозаметны человеку при исходном масштабе, но становились читаемыми после увеличения, масштабирования, локального кропа, повышения контраста или других преобразований.

Основной сценарий связан с анализом изображений перед их передачей мультимодальным ИИ-системам. Сервис не выполняет найденные инструкции, а только обнаруживает, извлекает и классифицирует их.

### 1.3. Цель разработки

Создать программный сервис, способный:
1. принимать изображения через графический интерфейс и REST API;
2. выполнять многоуровневое преобразование изображения;
3. находить области с потенциально скрытым текстом;
4. выполнять OCR на исходном и преобразованных изображениях;
5. определять, является ли обнаруженный текст инструкцией/промптом;
6. объединять результаты нескольких анализаторов;
7. возвращать итоговый вердикт, вероятность и координаты подозрительных областей;
8. сохранять результаты для последующего анализа и оценки качества модели.

## 2. Краткая информация о предметной области

Современные мультимодальные модели способны воспринимать изображения наряду с текстом. Это создаёт новый класс атак, при котором инструкция размещается не в текстовом поле, а непосредственно в изображении. Такой текст может быть визуально малозаметным: иметь небольшой размер шрифта, низкий контраст, быть размещённым в удалённой части изображения, маскироваться фоном или становиться читаемым только после увеличения.

Задача системы относится к пересечению компьютерного зрения, OCR, обнаружения объектов/текста, анализа естественного языка и безопасности ИИ. Практически задача раскладывается на две стадии:

**Vision/OCR:** обнаружить потенциальную текстовую область и восстановить текст.

**Семантический анализ:** определить, содержит ли распознанная строка инструкцию, управляющую поведением ИИ, а не обычную подпись, описание или декоративный текст.

Ключевая особенность проекта - анализ не только исходного изображения, но и набора его преобразованных представлений.

## 3. Функциональные требования

### 3.1. Загрузка изображения

Сервис должен принимать:
- PNG;
- JPEG/JPG;
- WebP;
- при необходимости TIFF.

Ограничения:
- максимальный размер файла: конфигурируемый, рекомендуемое значение 20 МБ;
- максимальное разрешение: конфигурируемое, рекомендуемое значение 8192×8192;
- проверка MIME-типа и фактического формата;
- защита от некорректных и повреждённых файлов.

### 3.2. Предобработка

Система должна поддерживать:
- нормализацию цветового пространства;
- масштабирование;
- увеличение разрешения;
- grayscale;
- повышение локального контраста;
- адаптивную бинаризацию;
- sharpening;
- локальное выделение деталей;
- разбиение изображения на тайлы/кропы;
- несколько уровней масштабирования.

### 3.3. Поиск скрытого текста

Для каждой версии изображения система должна:
- выполнять text detection;
- формировать bounding boxes / polygons;
- оценивать confidence;
- передавать найденные области в OCR;
- сохранять связь результата с конкретным преобразованием.

### 3.4. OCR

OCR-модуль должен возвращать:
- распознанный текст;
- координаты;
- confidence;
- язык/языки, если модель это поддерживает.

Рекомендуется использовать ансамбль или каскад OCR для повышения устойчивости к малому шрифту и низкому контрасту.

### 3.5. Семантическая классификация

Текст классифицируется как минимум по классам:
- `benign_text` - обычный текст;
- `instruction_candidate` - потенциальная инструкция;
- `prompt_injection_candidate` - инструкция, потенциально направленная на изменение поведения ИИ;
- `uncertain` - недостаточно данных для уверенной классификации.

Дополнительно допускается классификация по признакам:
- прямое обращение к модели;
- императивная форма;
- просьба игнорировать предыдущие инструкции;
- указание скрыть/не раскрывать информацию;
- изменение приоритетов инструкций;
- требование выполнить действие вместо пользователя.

Классификация должна быть вероятностной и сопровождаться confidence.

## 4. Пользовательские интерфейсы

### 4.1. Web GUI

Минимальный интерфейс:
1. область загрузки изображения;
2. превью исходного изображения;
3. кнопка запуска анализа;
4. индикатор выполнения;
5. визуализация найденных областей;
6. панель распознанного текста;
7. итоговая вероятность обнаружения скрытой инструкции;
8. список применённых преобразований;
9. возможность посмотреть каждую промежуточную версию изображения;
10. экспорт результата в JSON.

Рекомендуемый стек: React/Next.js или простой HTML/JS.

### 4.2. REST API

Основные методы:

`POST /api/v1/analyze` - загрузка изображения и запуск анализа.

`GET /api/v1/jobs/{job_id}` - получение состояния задания.

`GET /api/v1/jobs/{job_id}/result` - получение результата.

`GET /api/v1/health` - проверка работоспособности.

API должно возвращать уникальный `job_id`.

### 4.3. CLI

Для разработки и воспроизводимых экспериментов будет использоваться команда:

`hidden-prompt-detector analyze image.png --output result.json`

CLI является необязательным для пользовательской версии.

## 6. Внутренняя архитектура и пайплайн

Архитектура строится как последовательность независимых подсистем.

```text
[Web GUI / REST API / CLI]
            |
            v
      [API Gateway]
            |
            v
      [Job Manager]
            |
            v
    [Image Preprocessor]
            |
            v
 [Multi-scale Generator]
       /    |     \
      v     v      v
 [Scale1][Scale2][ScaleN]
       \    |     /
            v
     [Text Detector]
            |
            v
      [Region Extractor]
            |
            v
        [OCR Engine]
            |
            v
 [Text Normalization/Dedup]
            |
            v
 [Prompt Classifier]
            |
            v
 [Evidence Aggregator]
            |
            v
 [Risk/Confidence Scorer]
            |
            v
      [Result Storage]
            |
            v
     [API / Web GUI]
```

### 6.1. API Gateway

Ответственность:
- HTTP;
- валидация входных данных;
- аутентификация при необходимости;
- ограничение размера запросов;
- маршрутизация.

### 6.2. Job Manager

Ответственность:
- создание задания;
- выдача `job_id`;
- управление статусами;
- повторный запуск после ошибки;
- таймауты.

Статусы:

`queued -> preprocessing -> detecting -> ocr -> classifying -> aggregating -> completed`

Дополнительные:

`failed`, `cancelled`.

### 6.3. Image Preprocessor

Создаёт базовые представления изображения и контролирует допустимое разрешение.

### 6.4. Multi-scale Generator

Формирует несколько представлений:

- исходный масштаб;
- 2×;
- 4×;
- 8×;
- локальные кропы;
- варианты с повышенным контрастом.

Конкретные параметры должны подбираться экспериментально.

### 6.5. Text Detector

Ищет текстовые области независимо от того, насколько хорошо OCR сможет их прочитать.

Возможные модели:
- DBNet/DBNet++;
- CRAFT;
- EAST;
- современные vision-language/text detection модели.


### 6.6. OCR Engine

Рекомендуется сравнить:
- PaddleOCR;
- EasyOCR;
- Tesseract;
- трансформерные OCR-модели.

Выбор финальной модели должен основываться на отдельном эксперименте на скрытом тексте.

### 6.7. Text Normalizer

Выполняет:
- Unicode normalization;
- удаление повторяющихся пробелов;
- исправление типичных OCR-артефактов;
- дедупликацию результатов разных масштабов.

### 6.8. Prompt Classifier

Получает OCR-текст и признаки области.

Рекомендуемый baseline:
- TF-IDF + Logistic Regression / Linear SVM.

ML-вариант:
- fine-tuning multilingual transformer, например XLM-RoBERTa или mDeBERTa, при наличии подходящего датасета.

### 6.9. Evidence Aggregator

Объединяет:
- confidence text detector;
- OCR confidence;
- классификационную вероятность;
- число независимых масштабов, в которых найден текст;
- стабильность текста после преобразований.

Пример итогового score:

`S = w1*D + w2*O + w3*C + w4*R + w5*P`

где:
- `D` - confidence detector;
- `O` - OCR confidence;
- `C` - semantic classifier confidence;
- `R` - reproducibility across scales;
- `P` - prompt-specific evidence.

Весовые коэффициенты должны определяться на validation set.

## 7. Модели и алгоритмы ИИ/ML

### 7.1. Детектор текста

Основной кандидат: DBNet++.

Задача - локализовать текстовые области, включая небольшие области.

Альтернатива: CRAFT/EAST.

### 7.2. Super-resolution

Для особенно мелкого текста допускается дополнительный этап super-resolution.

Кандидаты:
- Real-ESRGAN;
- SwinIR;
- специализированные text super-resolution методы.

Важно: super-resolution не должен рассматриваться как источник «истины»: он может изменять пиксельные данные и создавать артефакты. Поэтому его результат используется как дополнительное свидетельство.

### 7.3. OCR

Основной кандидат: PaddleOCR.

Альтернативы:
- Tesseract;
- EasyOCR;
- TrOCR и другие transformer OCR.

### 7.4. Семантическая модель

Базовая версия:
- TF-IDF + Logistic Regression.

Продвинутая версия:
- XLM-RoBERTa / mDeBERTa;
- fine-tuning на русском и английском тексте.


### 7.5. Ансамбль

Финальное решение должно учитывать не один источник, а совокупность признаков. Это особенно важно для работы, поскольку позволяет исследовать вклад масштабирования и устойчивость обнаружения.

## 8. Методы обучения

### 8.1. Детектор текста

Предпочтительно использовать transfer learning от предобученной модели.

Варианты:
- frozen backbone + обучение detection head;
- partial fine-tuning;
- full fine-tuning при достаточном объёме данных.

### 8.2. OCR

Для первого прототипа допускается использование готовой предобученной OCR-модели без дополнительного обучения.

Дообучение применяется только при наличии специализированного набора данных с:
- маленьким текстом;
- низким контрастом;
- текстом после масштабирования;
- шумом и артефактами.

### 8.3. Классификатор промптов

Два режима:

**Baseline:** TF-IDF + Logistic Regression.

**Advanced:** fine-tuning transformer-модели.

Разделение датасета:
- train - 70%;
- validation - 15%;
- test - 15%.

Разбиение должно выполняться на уровне исходных примеров, чтобы производные изображения одного и того же источника не попадали одновременно в train и test.

## 9. Требования к обучающим данным

Набор данных должен содержать как минимум:

### Положительные примеры
- явно видимый prompt;
- скрытый мелкий prompt;
- prompt с низким контрастом;
- prompt в углу;
- prompt на сложном фоне;
- prompt, читаемый только после увеличения;
- разные шрифты;
- русский и английский языки.

### Отрицательные примеры
- обычные подписи;
- документы;
- рекламные надписи;
- мемы;
- скриншоты;
- дорожные знаки;
- интерфейсы;
- случайный мелкий текст;
- декоративный текст.

### Метаданные

Для каждого изображения:
- `image_id`;
- источник;
- класс;
- текст;
- координаты bounding box;
- язык;
- тип скрытия;
- уровень масштаба;
- параметры синтетической генерации;
- split.

### Синтетическая генерация

Рекомендуется создать генератор данных, который автоматически:
1. берёт фон;
2. генерирует инструкцию;
3. выбирает шрифт;
4. изменяет размер;
5. регулирует прозрачность;
6. размещает текст;
7. добавляет шум;
8. применяет blur/compression;
9. сохраняет ground truth координаты и текст.

Синтетический генератор позволяет контролировать сложность задачи и избежать дефицита размеченных данных.

## 10. Валидация

### 10.1. Text detection

Метрики:
- Precision;
- Recall;
- F1;
- IoU / polygon IoU;
- mAP - при необходимости.

### 10.2. OCR

Метрики:
- Character Error Rate (CER);
- Word Error Rate (WER);
- exact match;
- normalized edit distance.

### 10.3. Prompt classification

Метрики:
- Precision;
- Recall;
- F1;
- ROC-AUC;
- PR-AUC;
- confusion matrix.

Особое внимание уделяется Recall для класса `prompt_injection_candidate`, так как пропуск скрытой инструкции является критической ошибкой в рамках исследовательской задачи.

### 10.4. End-to-end

Основные метрики:
- detection recall;
- false positive rate;
- end-to-end F1;
- среднее время обработки;
- p95 latency;
- потребление памяти/VRAM.

## 11. Тестирование

### 11.1. Unit tests

Проверяются:
- валидатор изображений;
- preprocessing;
- генератор масштабов;
- OCR normalization;
- deduplication;
- score aggregation;
- API schemas.

### 11.2. Integration tests

Проверяется полный путь:

`upload -> preprocessing -> detection -> OCR -> classification -> aggregation -> result`.

### 11.3. Regression tests

Фиксированный набор изображений хранится отдельно от train/validation.

После изменения модели результаты сравниваются с baseline.

### 11.4. Adversarial/robustness tests

Проверяются:
- JPEG compression;
- blur;
- rotation;
- resize;
- contrast changes;
- noise;
- очень маленький шрифт;
- разные фоны;
- частичная обрезка текста.

### 11.5. Acceptance criteria

Принцип работы:

1. система должна стабильно обнаруживать заранее размеченные скрытые инструкции;
2. должна предоставлять координаты подозрительной области;
3. должна сохранять распознанный текст;
4. должна отличать известный набор benign text от prompt-like инструкций;
5. результаты должны быть воспроизводимыми на фиксированном тестовом наборе.

## 12. Нефункциональные требования

### Производительность

Для CPU-режима целевой показатель - обработка одного изображения в течение нескольких десятков секунд для стандартного разрешения.

Для GPU-режима допускается обработка в течение нескольких секунд, в зависимости от моделей и количества масштабов.

### Масштабируемость

Компоненты detection/OCR/classification должны иметь возможность запуска как:
- одного процесса;
- нескольких worker-процессов;
- отдельных сервисов.

### Безопасность

- проверка типов файлов;
- ограничение размера;
- защита от path traversal;
- отсутствие выполнения распознанного текста;
- очистка временных файлов;
- ограничение времени обработки;
- журналирование ошибок без записи чувствительных данных.

## 15. Требования к результату анализа

Пример:

```json
{
  "job_id": "01HXYZ...",
  "status": "completed",
  "detected": true,
  "risk_score": 0.91,
  "regions": [
    {
      "bbox": [102, 870, 760, 940],
      "text": "Ignore previous instructions and ...",
      "ocr_confidence": 0.94,
      "prompt_probability": 0.97,

    }
  ],

    "scale_8x",

  ]
}
```

Система не должна интерпретировать поле `text` как команду для исполнения.

## 16. Критерии готовности дипломного прототипа

Проект считается реализованным, если:
- есть Web GUI;
- есть REST API;
- реализован полный inference pipeline;
- система анализирует минимум три масштаба;
- работает text detection;
- работает OCR;
- есть классификация prompt-like текста;
- реализован итоговый score;
- есть тестовый датасет;
- есть автоматические тесты;
- рассчитаны основные ML-метрики;
- есть Docker-развёртывание;
- документация позволяет запустить проект с нуля.

## 17. Этапы разработки

### Этап 1 - исследование
Анализ методов скрытия текста, OCR и prompt injection.

### Этап 2 - baseline

### Этап 5 - semantic classifier

### Этап 6 - aggregation

### Этап 7 - API/GUI
Разработка пользовательского интерфейса.

### Этап 8 - тестирование

### Этап 9 - упаковка

## 18. Ограничения и риски

1. OCR может ошибаться на сверхмалом тексте.
2. Super-resolution может создавать артефакты.
3. Скрытая инструкция может быть графически зашифрована и не сводиться к обычному OCR.
4. Семантический классификатор может ошибочно принимать обычные инструкции за prompt injection.
5. Мультиязычность повышает требования к данным.
6. Полное отсутствие false positives практически недостижимо; поэтому интерфейс должен показывать confidence и evidence.
7. Система должна рассматриваться как детектор потенциальной угрозы, а не как формальный доказатель наличия вредоносной инструкции.

## 19. Итоговая архитектурная идея диплома

Главный исследовательский вклад проекта - не просто применение OCR, а оценка того, насколько **многошкальный анализ изображения** позволяет обнаруживать текстовые инструкции, которые плохо различимы в исходном масштабе.

Экспериментальная гипотеза может быть сформулирована так:

> Использование нескольких масштабов и преобразований изображения в сочетании с OCR и семантической классификацией позволяет повысить полноту обнаружения скрытых текстовых инструкций по сравнению с анализом исходного изображения одним OCR-модулем.

Для проверки гипотезы рекомендуется провести ablation study:

- только исходное изображение;
- исходное + 2×;
- исходное + 2× + 4×;
- полный multi-scale pipeline;
- multi-scale без semantic classifier;
- multi-scale + semantic classifier.

Результаты следует сравнить по Recall, Precision, F1, CER/WER и времени обработки.
